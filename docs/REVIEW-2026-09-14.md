# Architecture review: Zettle follow-ups, image export, staging automation

Reviewer: Fable (lead architect), 2026-09-14. Scope: Astra's merges since
[ZETTLE-REVIEW-2026-09-13.md](ZETTLE-REVIEW-2026-09-13.md): PR112 (receipt
timestamp tolerance, migration `20260915170000`), PR114 (product image
export, migration `20260915190000`, `extensions/zettle/images.ts`,
`lib/engine/zettle-images.ts`, pgTAP 0063) and PR117 (staging migrations
from CI, `scripts/migrate-staging.mjs`, the `staging-migrations` job).
Nothing in Astra's code was changed by this review; the PR that carries it
only adds the deploy-gap tolerance (finding 1) to Fable's own reads.

## Verdict

All three follow the hard rules. No core table is written outside the
engine, every new table is owner/admin-scoped with a restrictive policy and
an immutability trigger, provider URLs are allowlisted twice (zod and a SQL
check), the storage download runs under the user's session, and the CI
deployment uses a management token held in a GitHub environment rather than
a database password or service key in the application. I found no
access-control or isolation gap. The findings are operational.

## Findings

1. **The application can deploy before its migration for about ten
   minutes.** Vercel builds on every push to main at once; the
   `staging-migrations` job runs after the platform check (about eight
   minutes) and then applies. A page that calls a new RPC in that gap fails.
   Astra's image slice hides itself on PostgREST's missing-function code
   (`PGRST202`); Fable's Fortnox and brief slices do not, so the accounting
   and economy pages would error for those minutes after a merge that adds
   an RPC they call. Two ways out, in order of preference: (a) turn off
   Vercel's automatic deployment for main and trigger a deploy hook from the
   workflow after the `staging-migrations` job succeeds, so the order is
   always database first (owner action in Vercel, one `curl` step in the
   workflow); (b) until then, every new page read tolerates `PGRST202` the
   way `readZettleImages` does. Fable takes (b) for the Fortnox and brief
   reads; (a) is an owner decision recorded in
   [PILOT-GATES.md](PILOT-GATES.md).

2. **The timestamp tolerance closes the deadlock for skew, not for a stuck
   page.** `record_zettle_pull_page` now accepts purchases from five minutes
   before the window start (bounded below by the activation cutover) to five
   minutes after its end. A purchase outside that band still fails the same
   page on every retry with no operator escape. Acceptable for the manual
   pilot where a person watches; before scheduled retrieval, add the owner
   command that closes a window with a recorded reason (finding 1 of the
   previous review, second option).

3. **Image export keeps two claims in step by re-reading its own intent.**
   `exportZettleImage` calls `prepare_zettle_image` again before the upload
   and before the product PUT (`requireCurrent`) and stops on any change.
   Correct, and the intent row is immutable, so a lost upload response leaves
   an orphan at the provider that a person reconciles, as the document says.
   One gap: `zettle_item_image_url` and `zettle_image_status` are owner/admin
   only, while the stock export status is visible to staff on the same page;
   staff see the product as exported and no photo state. Cosmetic; align
   the read roles when the page is next touched.

4. **The staging job parses history strictly and refuses divergence.** Good:
   a remote version missing locally stops the run instead of repairing, and
   the job never runs on pull requests. Two things the document asks of the
   owner that code cannot check: the `staging-database` environment must
   restrict deployment branches to main, and the management token must be
   the staging account's. Both belong in the pilot gate list.

5. **Test file numbers still collide.** 0063 was taken by both
   `zettle_images` (Astra) and, before renumbering, `fortnox_connection`
   (Fable). The rule stands: glob `supabase/tests` across every worktree
   before numbering. Fable is at 0066; Astra should start at 0070 to leave
   room.

## Addendum, same day: PR126 to PR130

Read after Astra took the rewritten task list: PR126 (window escape,
migration `20260916000000`), PR127 (engine VAT rate beside the map), PR128
(retire the staged `recordZettlePurchase` TypeScript path), PR129 (staff
image reads, migration `20260916010000`) and PR130 (live evidence log).
All follow the rules; nothing blocks a merge. Two notes for the record:

- `abandon_zettle_pull_window` is owner only while `open_zettle_pull_window`
  is owner or admin. Stricter is fine for an escape hatch; the document
  should say so in one line so an admin does not read the refusal as a bug.
- `zettle_image_status_v2` exists only so a staff page can tell the old
  owner-only function from the new one during the deploy gap. Acceptable
  once; the general rule stays: one function name, `create or replace` in a
  new migration, and reads that tolerate `PGRST202`. When the deploy hook
  (PILOT-GATES.md) is in place the gap disappears and `_v2` can be retired
  in a later migration.

## Addendum, evening: PR149 and PR153

PR149 (Fortnox send replay safety, migration `20260916080000`, pgTAP
`0080`, `scripts/fortnox-send-race.mjs`) is right and changed the rule:
only a fresh `begin_fortnox_send` may POST, a pending send is held
regardless of age, a lost response after the POST is recorded as
`FORTNOX_OUTCOME_UNKNOWN`, and only a proven preflight failure may be
retried. The earlier answer's retry paragraph was withdrawn and the
reconciliation design (`reconcile_fortnox_send` with `confirmed_sent` or
`confirmed_absent` on recorded evidence, a read-only voucher list as the
evidence helper) is in FABLE_TO_ASTRA_ANSWERS.md. The two existing tests
that PR149 adjusted (`0065`, `0067`) now start a fresh send before every
completion, which is the correct reading of the invariant. No findings.

PR153 (OPERATIONS-MFA-RECOVERY.md) is a procedure only: owner verifies the
person through an independent channel, the operator removes the approved
factor in the Supabase dashboard under a support record, the person
re-enrols, and a synthetic staging exercise gates the pilot. No service
key, no SQL against Auth tables, no application change. Consistent with
decision B2. No findings.
