## Architecture and scope

Use Komisio's shared-engine/staged-operation boundaries, as documented
in RECEPTION-ARCHITECTURE.md and HOW-AI-FITS.md. Do not claim current upstream
parity without checking it. Old Komisio supplies workflow questions, not schema.

- Engine: authorized reads, commands, revision validation and deterministic rules.
- Database: authoritative identities, isolation, immutable facts and constraints.
- Skills: domain guidance and uncertainty, never authorization or financial truth.
- AI adapters: sourced suggestions and explicit scope/cost limits.
- UI/MCP: thin adapters to the same operations; no separate business-rule copies.
- Tenant configuration: typed supported policies, not arbitrary instructions.

An approved review is not physical receipt, completed contract onboarding,
commercial acceptance, sellable inventory or a payable seller balance. Full
commercial acceptance requires resolution of the exact terms frozen per item;
see open-questions.md. Do not create a broad item/VAT/settlement schema today.
No new real email, paid AI configuration, purchases, payments, DNS changes or
external POS writes. Staging may expose completed functions under existing owner
authorization; preserve the owner's records and never respond for their seller.

## Checkpoint and release protocol

1. Before each slice: inspect clean/dirty Git state, open PRs and latest handover;
   name one bounded outcome and mark it IN_PROGRESS. Preserve unfinished work.
2. Record any new rule/assumption before implementation. Database rules need tests
   before the additive migration. Do not modify any applied migration.
3. Run relevant local checks. Application changes need lint/typecheck/build and
   appropriate unit/browser checks; DB changes need pgTAP and race checks when
   concurrency is affected. Test actual Storage HTTP paths for photo changes.
4. Write a checkpoint BEFORE a lengthy test, external migration or merge. Include
   exact next command and recovery action if interrupted; no tokens or secrets.
5. Use signed-off commits, scoped PRs and self-review. Require green CI on the
   exact PR head before merge. Apply only expected migrations to the expected
   staging project; record migration and merge/deployment separately.
6. Verify the staged outcome, not only a healthy homepage. Label any hosted
   user-only verification still outstanding. Update the handover after each slice.
7. At the deadline, a usage limit or interruption: start no new slice. Save work,
   record every uncommitted file, running process, open PR and next step. A WIP
   branch/commit is acceptable but must never be described as tested or merged.
